## 1. 背景と目的

### 1.1 現状の課題

問い合わせ窓口の共有メールアドレスに、1日あたり数十通のメールが届く。内訳は新規の問い合わせ、見積依頼、既存顧客からのサポート依頼、日程調整、業者からの営業、システムの自動通知が入り混じっている。

現在は担当者が朝と夕方に受信トレイを開き、1通ずつ読んで振り分けている。この作業には次の問題がある。

| 課題 | 具体的な内容 |
|---|---|
| 対応漏れ | 営業メールと自動通知に紛れて、見積依頼の見落としが月に1〜2件発生している |
| 属人化 | 振り分けの基準が担当者の頭の中にあり、引き継ぎができない |
| 一次対応の遅さ | 担当者が受信トレイを開くまで最大で半日、返信が始まらない |
| 記録が残らない | 「いつ何件どんな問い合わせが来たか」を後から集計できない |

### 1.2 目的

**メールの下処理を機械が行い、人間は判断だけを行う状態にする。**

具体的には次の3点を達成する。

1. 受信したメールを分類し、要対応のものだけを担当者に通知する
2. 全件を記録し、後から件数・傾向を集計できるようにする
3. 定型的な返信の下書きを事前に用意し、返信開始までの時間を短縮する

### 1.3 スコープ外

明示的に対象外とするもの。

- **メールの自動送信** — 下書きの作成までを対象とし、送信は必ず人が行う。AIの判断で顧客にメールが飛ぶ状態は作らない
- **添付ファイルの解析** — 本文のみを分類対象とする
- **顧客管理システム（CRM）との連携** — 将来的な拡張候補にとどめる
- **複数メールアドレスの同時処理** — 対象は1つの共有アドレスとする

## 2. 業務要件

### 2.1 業務フロー（導入後）

| # | 実施主体 | 内容 |
|---|---|---|
| 1 | システム | 平日 9:00 / 13:00 / 17:00 に未読メールを取得する |
| 2 | システム | 各メールを7区分（6分類＋保留）に分類し、要約を作成する |
| 3 | システム | 全件をスプレッドシートに追記する |
| 4 | システム | 要対応のもの（保留を含む）だけをSlackに通知する |
| 5 | システム | 要対応かつ返信が必要なものについて、返信下書きをGmailに作成する |
| 6 | **担当者** | Slack通知を見て、対応要否と優先度を判断する |
| 7 | **担当者** | Gmailの下書きを確認・修正し、送信する |
| 8 | **担当者** | 保留となったメールを目視で確認し、対応する |

### 2.2 分類区分

| key | 区分 | 定義 | 通知 | 下書き |
|---|---|---|:---:|:---:|
| `inquiry` | 新規問い合わせ | 取引のない相手からの問い合わせ | ○ | ○ |
| `quote_request` | 見積依頼 | 金額の提示を求めるもの | ○ | ○ |
| `existing_support` | 既存顧客サポート | 既存顧客からの不具合報告・操作の質問 | ○ | ○ |
| `appointment` | 日程調整 | 打ち合わせの日程に関するもの | ○ | ○ |
| `vendor_sales` | 営業・売り込み | 業者からの提案・案内 | – | – |
| `notification` | 自動通知 | システムからの自動送信メール | – | – |
| `unclassified` | **保留** | **上記のいずれとも判断できないもの、または判断の確信が持てないもの** | **○** | – |

### 2.3 保留区分の位置づけ

**この仕組みで最も重要な区分。**

AIによる分類は必ず外れる。問題は外れること自体ではなく、外れたことに誰も気づかないまま処理が進むことにある。見積依頼が「営業メール」に分類されれば、そのメールは通知されず、誰の目にも触れずに失注する。

そのため、分類器には判定と同時に**確信度（0.0〜1.0）**を出力させ、以下の場合は分類結果を破棄して保留に倒す。

- 分類器が `unclassified` と判定した場合
- 確信度が閾値（既定 0.6）を下回った場合

保留は必ず通知され、人が目視で確認する。**「AIが分からなかったもの」が確実に人間に渡ることを、この仕組みは保証する。**

## 3. 機能要件

| ID | 機能 | 内容 | 優先度 |
|---|---|---|---|
| F-01 | メール取得 | 指定条件（Gmail検索構文）に一致するメールを取得する。1回の上限件数を設定できる | 必須 |
| F-02 | 分類 | メールを7区分に分類し、確信度・要約・判断根拠を出力する | 必須 |
| F-03 | 保留判定 | 確信度が閾値未満の分類を保留に倒す。閾値は設定で変更できる | 必須 |
| F-04 | 記録 | 全件をスプレッドシートに追記する。処理日時・受信日時・差出人・件名・分類・確信度・要約を残す | 必須 |
| F-05 | 通知 | 要対応の区分のみをSlackに通知する。保留は必ず通知する | 必須 |
| F-06 | 返信下書き | 要対応かつ返信が必要なものについて、Gmailに下書きを作成する。**送信はしない** | 必須 |
| F-07 | 重複防止 | 処理済みメッセージIDを記録し、再実行時に二重処理しない | 必須 |
| F-08 | ドライラン | 分類までを実行し、記録・通知・下書き作成を行わないモード | 必須 |
| F-09 | デモ実行 | APIキー・ネットワークなしでサンプルデータを処理するモード | 必須 |
| F-10 | 定期実行 | 平日の指定時刻に自動実行する | 必須 |
| F-11 | 手動実行 | 任意のタイミングで実行できる | 必須 |

## 4. 非機能要件

### 4.1 信頼性

| ID | 要件 |
|---|---|
| N-01 | 1通の処理が失敗しても、残りのメールの処理を継続すること |
| N-02 | 処理に失敗したメールは処理済みとして記録せず、次回の実行で再処理されること |
| N-03 | 外部APIの一時的な失敗（レート制限・5xx・接続断）は自動で再試行すること（最大3回・指数バックオフ） |
| N-04 | 設定不備・認証エラーなど再試行しても回復しないエラーは即座に失敗させ、原因を明示すること |
| N-05 | 同じ入力に対して何度実行しても、記録・通知・下書きが重複しないこと |

### 4.2 運用性

| ID | 要件 |
|---|---|
| N-06 | 実行ログは機械的に解析可能な形式（1行1JSON）で出力すること |
| N-07 | ログに認証情報・APIキーを含めないこと |
| N-08 | 設定の不備は処理開始前に検出し、何をどう直せばよいかを示すこと |
| N-09 | エンジニアでない担当者が初期設定を実施できる手順書を用意すること |
| N-10 | 外部サービスに接続せずに動作確認できる手段を用意すること |

### 4.3 安全性

| ID | 要件 |
|---|---|
| N-11 | メールの自動送信を行わないこと。下書きの作成までとする |
| N-12 | 確信度が閾値未満の分類に基づく返信下書きを作成しないこと |
| N-13 | 認証情報はリポジトリに含めず、環境変数（GitHub Secrets）で受け渡すこと |
| N-14 | Gmailの権限は読み取りと下書き作成に限定し、送信権限を与えないこと |

### 4.4 性能・コスト

| ID | 要件 |
|---|---|
| N-15 | 1回の実行は10分以内に完了すること |
| N-16 | 1回の実行で処理する件数に上限を設けられること（暴走時のコスト防止） |
| N-17 | 分類1件あたりのAPI利用料が実運用に耐える水準であること（本文は上限文字数で切り詰める） |

### 4.5 拡張性

| ID | 要件 |
|---|---|
| N-18 | 分類器・取得元・記録先・通知先を、他の実装に差し替えられる構造とすること |
| N-19 | 分類区分の追加・変更が1ファイルの修正で完結すること |

## 5. システム構成

### 5.1 全体像

```
GitHub Actions（平日 9:00 / 13:00 / 17:00 JST）
  └─ Node.js (TypeScript)
       ├─ Gmail API      … 未読メールの取得、返信下書きの作成
       ├─ Claude API     … 分類・要約・下書き生成
       ├─ Sheets API     … 処理結果の記録
       └─ Slack Webhook  … 要対応メールの通知
```

### 5.2 技術選定

| 項目 | 選択 | 理由 |
|---|---|---|
| 言語 | TypeScript (Node 20+) | 型で分類区分・データ構造を表現でき、区分の追加漏れをコンパイル時に検出できる |
| AI | Claude API (`claude-opus-5`) | 構造化出力により、分類結果を型定義そのままの形で受け取れる |
| 実行基盤 | GitHub Actions | サーバの調達・運用が不要。実行履歴がそのまま監査ログになる |
| 記録先 | Googleスプレッドシート | 業務側が自分で開き、絞り込み、列を足せる。DBにすると必ず問い合わせが発生する |
| 通知 | Slack Incoming Webhook | 既存の業務チャンネルに載せられる |
| 認証 | サービスアカウント + ドメイン全体の委任 | ブラウザ操作を伴わないため無人実行に適する |

### 5.3 データ項目（スプレッドシート）

| 列 | 項目 | 例 |
|---|---|---|
| A | 処理日時 | 2026-09-04T09:00:12.000Z |
| B | 受信日時 | 2026-09-03T10:04:00+09:00 |
| C | メッセージID | 18f2a1b3c4d5e6f7 |
| D | 差出人 | suzuki@example.co.jp |
| E | 件名 | 【見積依頼】システム開発費用について |
| F | 分類 | 見積依頼 |
| G | 確信度 | 0.90 |
| H | 要約 | 在庫管理システムの見積依頼。想定30名、納期2027年3月末。 |

保留に倒れた場合、F列は `保留（要目視）（元判定: quote_request）` の形式で元の判定も残す。後から閾値の妥当性を検証するために必要。

## 6. 制約事項

| ID | 内容 |
|---|---|
| C-01 | Gmailのサービスアカウント利用にはGoogle Workspaceの管理者権限が必要（ドメイン全体の委任の設定） |
| C-02 | GitHub Actions の cron は指定時刻ちょうどには起動せず、数分〜十数分の遅延が発生しうる |
| C-03 | 処理済みIDの保存先はGitHub Actionsのartifact（保持期間90日）。単一実行を前提とし、並列実行には対応しない |
| C-04 | Claude APIの利用料が発生する。1回の処理件数に上限を設けて制御する |
| C-05 | スレッドの過去のやり取りは参照せず、1通ごとに独立して分類する |

## 8. 段階的な導入計画

いきなり全自動にしない。信用を積んでから権限を渡す。

| 期間 | 段階 | 内容 |
|---|---|---|
| 第1〜2週 | ドライラン | `--dry-run` で分類結果だけを確認する。担当者の判断と突き合わせ、閾値を調整する |
| 第3〜4週 | 記録・通知のみ | スプレッドシートへの記録とSlack通知を開始する。返信下書きは作らない。従来の目視確認も並行して続ける |
| 第5週〜 | 下書き作成を追加 | 返信下書きの作成を有効にする。送信は引き続き人が行う |
| 第7週〜 | 従来運用の停止 | 保留率と対応漏れの発生状況を確認したうえで、目視での全件確認をやめる |

第1〜2週で確認すべきこと。

- 保留率が高すぎないか（多すぎると人手が減らない。目安として2割を超えるならプロンプトか閾値を見直す）
- 保留率が低すぎないか（誤分類を見逃している可能性。閾値を上げて様子を見る）
- 分類が担当者の感覚と一致しているか
