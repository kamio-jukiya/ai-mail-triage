このツールを実際に動かすための手順書です。**プログラミングの知識がなくても設定できるよう**、画面上の操作を順番に書いています。

## 1. このツールが何をするか

平日の **9時・13時・17時** に自動で動き、次のことをします。

| # | やること |
|---|---|
| 1 | 指定した Gmail の受信トレイから、未読メールを取り出す |
| 2 | AIが1通ずつ読んで、7つの区分に分ける |
| 3 | すべてのメールをスプレッドシートに1行ずつ記録する |
| 4 | 対応が必要なものだけ Slack に通知する |
| 5 | 返信が必要なものについて、Gmailに返信の**下書き**を作る |

### 大事なこと

> **メールが勝手に送信されることはありません。**
> このツールが作るのは「下書き」までです。送信ボタンを押すのは必ず人です。

> **AIが判断できなかったメールは「保留」になり、必ずSlackに通知されます。**
> AIの判断が怪しいものを黙って処理してしまわないための仕組みです。保留の通知が来たら、そのメールは人が直接見てください。

### 7つの区分

| 区分 | どんなメールか | Slack通知 | 下書き |
|---|---|:---:|:---:|
| 新規問い合わせ | 初めての相手からの問い合わせ | ○ | ○ |
| 見積依頼 | 金額を聞かれているもの | ○ | ○ |
| 既存顧客サポート | 取引先からの不具合報告・質問 | ○ | ○ |
| 日程調整 | 打ち合わせの日程の話 | ○ | ○ |
| 営業・売り込み | 業者からの提案メール | 通知しない | 作らない |
| 自動通知 | システムからの自動メール | 通知しない | 作らない |
| **保留（要目視）** | **AIが判断できなかったもの** | **○** | 作らない |

営業と自動通知を通知しないのは意図的です。全部通知すると通知そのものが読まれなくなり、仕組み全体が意味を失います。

## 2. 準備するもの

設定を始める前に、次のものを用意してください。**すべて揃ってから作業を始めてください。**

| # | 必要なもの | 入手方法 | 誰が用意するか |
|---|---|---|---|
| 1 | Anthropic の APIキー | https://console.anthropic.com/ で発行 | 担当者（クレジットカード登録が必要） |
| 2 | Google Workspace の管理者権限（**個人のGmailを使う場合は不要**） | 社内の情報システム担当に依頼 | 情報システム担当 |
| 3 | 対象の Gmail アドレス | 例: `info@あなたの会社.co.jp` | 担当者 |
| 4 | 記録用のスプレッドシート | Googleドライブで新規作成 | 担当者 |
| 5 | Slack の通知先チャンネル | 既存のチャンネルでよい | 担当者 |
| 6 | GitHub のリポジトリ | このツールを置く場所 | 担当エンジニア |

**所要時間の目安: 1〜2時間**（Google側の権限設定に一番時間がかかります）

## 3. 初期設定

### 3-1. Anthropic の APIキーを取得する

1. https://console.anthropic.com/ を開き、アカウントを作成します
2. クレジットカードを登録します（従量課金です）
3. 左メニューの「API Keys」を開きます
4. 「Create Key」を押し、名前に `mail-triage` と入力して作成します
5. 表示された `sk-ant-` で始まる文字列を**コピーして安全な場所に保存**します

> **注意:** このキーは作成直後の1回しか表示されません。閉じてしまったら作り直しになります。
> このキーは**パスワードと同じ**です。メールやチャットに貼り付けないでください。

---

### 3-2. Google の設定 — まず、どちらの方式かを選ぶ

**対象のメールアドレスによって手順が変わります。** 先にどちらか確認してください。

| 対象のメールアドレス | 使う方式 | 進む手順 |
|---|---|---|
| 会社の Google Workspace（`@自社ドメイン`） | サービスアカウント | **3-2A** |
| 個人の Gmail（`@gmail.com`） | OAuth | **3-2B** |

> **個人の Gmail では 3-2A は使えません。**
> サービスアカウント方式は「ドメイン全体の委任」という設定が前提で、これは Google Workspace の管理コンソールにしかありません。
> `@gmail.com` には委任元となるドメインが存在しないため、設定する画面自体がありません。個人のGmailを使うなら 3-2B に進んでください。

---

### 3-2A. Google Workspace の場合（情報システム担当と一緒に行う）

**Google Workspace の管理者権限が必要**です。個人のGmailを使う場合はここを飛ばして 3-2B へ進んでください。

#### (1) サービスアカウントを作る

1. https://console.cloud.google.com/ を開きます
2. 画面上部でプロジェクトを新規作成します（名前は `mail-triage` など）
3. 左メニュー「APIとサービス」→「ライブラリ」を開きます
4. `Gmail API` を検索して「有効にする」を押します
5. 同様に `Google Sheets API` も検索して「有効にする」を押します
6. 左メニュー「APIとサービス」→「認証情報」を開きます
7. 「認証情報を作成」→「サービスアカウント」を選びます
8. 名前に `mail-triage` と入力し、作成します
9. 作成されたサービスアカウントをクリックし、「キー」タブを開きます
10. 「鍵を追加」→「新しい鍵を作成」→ **JSON** を選びます
11. JSONファイルがダウンロードされます。**このファイルはパスワードと同じ扱い**です

#### (2) サービスアカウントに Gmail を読む権限を与える

この作業は **Google Workspace の管理者**が行います。

1. 手順(1)で作ったサービスアカウントの詳細画面で、**クライアントID**（数字の羅列）をコピーします
2. https://admin.google.com/ を開きます
3. 「セキュリティ」→「アクセスとデータ管理」→「APIの制御」→「ドメイン全体の委任」を開きます
4. 「新しく追加」を押します
5. クライアントIDに、手順1でコピーした数字を貼り付けます
6. OAuthスコープに、以下を**カンマ区切りで**貼り付けます

```
https://www.googleapis.com/auth/gmail.readonly,https://www.googleapis.com/auth/gmail.compose,https://www.googleapis.com/auth/spreadsheets
```

7. 「承認」を押します

> **なぜ送信権限を入れないのか:** 入れていないのは意図的です。`gmail.compose` は下書きの作成までしかできません。
> 万が一プログラムに不具合があっても、メールが顧客に送信されることは**技術的に起こりえません**。
> この2つ以外のスコープを足さないでください。

3-2A を実施した場合は、**3-2C. スプレッドシートを用意する**（3-2B の後にあります）へ進んでください。

---

### 3-2B. 個人の Gmail の場合（OAuth）

管理者権限は不要です。**本人のアカウントで1回だけ許可の操作を行い**、以降は自動で動きます。

#### (1) プロジェクトとAPIを用意する

1. https://console.cloud.google.com/ を開きます
2. 画面上部でプロジェクトを新規作成します（名前は `mail-triage` など）
3. 左メニュー「APIとサービス」→「ライブラリ」で `Gmail API` を検索し「有効にする」を押します
4. 同様に `Google Sheets API` も「有効にする」を押します

#### (2) OAuth同意画面を作り、「本番」に公開する

1. 左メニュー「APIとサービス」→「OAuth同意画面」を開きます
2. User Type は「外部」を選びます（個人のGmailでは「内部」は選べません）
3. アプリ名（`mail-triage` など）、サポートメール、デベロッパー連絡先に自分のアドレスを入力します
4. スコープの追加で、次の3つを選びます

```
https://www.googleapis.com/auth/gmail.readonly
https://www.googleapis.com/auth/gmail.compose
https://www.googleapis.com/auth/spreadsheets
```

5. テストユーザーに自分のGmailアドレスを追加します
6. **同意画面の「公開ステータス」を「本番環境」に切り替えます**（「アプリを公開」ボタン）

> ### ここが最大の罠です（必ず読んでください）
>
> **罠1: 「テスト」状態のままだと、7日ごとに止まります。**
> 公開ステータスが「テスト」のまま発行したリフレッシュトークン（次の手順で取得するもの）は、**7日で失効します**。
> 動作確認した1週間後、何も変えていないのに定期実行が毎回失敗するようになります。原因が分かりにくい種類の故障です。
> 手順6で「本番環境」に切り替えてから、次の(4)でトークンを取得してください。
>
> **罠2: `gmail.readonly` と `gmail.compose` は「制限付きスコープ」です。**
> Googleが特に慎重に扱う種類の権限で、審査を受けていないアプリのままだと、許可の途中で
> 「このアプリはGoogleで確認されていません」という警告画面が出ます（「詳細」→「（アプリ名）に移動」で進めます）。
> **自分1人で使う分にはこのまま運用できます。** ただし他の人にも使わせる場合は、
> 利用者数の上限や、Googleのアプリ審査が必要になります。他人に配る予定があるなら、その前に担当エンジニアに相談してください。

#### (3) 認証情報（クライアントID）を作る

1. 左メニュー「APIとサービス」→「認証情報」を開きます
2. 「認証情報を作成」→「OAuth クライアント ID」を選びます
3. アプリケーションの種類は **「デスクトップアプリ」** を選びます
4. 作成すると **クライアントID** と **クライアントシークレット** が表示されます。両方コピーして保存します

#### (4) リフレッシュトークンを取得する（1回だけ）

この作業だけはPCのターミナルで行います。担当エンジニアに依頼しても構いません。

```bash
npm install
```

プロジェクト直下に `.env` というファイルを作り、(3)の値を書きます。

```
GOOGLE_OAUTH_CLIENT_ID=（クライアントID）
GOOGLE_OAUTH_CLIENT_SECRET=（クライアントシークレット）
```

そのうえで次を実行します。

```bash
npm run auth:google
```

画面にURLが表示されるので、ブラウザで開き、**対象のGmailアカウント**で許可します。
（罠2の警告画面が出たら「詳細」→「（アプリ名）に移動」で進みます）

許可すると、ターミナルに次の形式で結果が出ます。

```
GOOGLE_OAUTH_REFRESH_TOKEN=1//0e...
```

**この値もパスワードと同じ扱い**です。手順3-4でGitHubに登録します。

> リフレッシュトークンが表示されず「同じアカウントで過去に許可済みの場合に起きます」と出た場合は、
> https://myaccount.google.com/permissions でこのアプリのアクセスを解除してから、もう一度実行してください。

### 3-2C. スプレッドシートを用意する（3-2A / 3-2B 共通）

1. Googleドライブで新しいスプレッドシートを作ります（名前は「メール振り分け記録」など）
2. 左下のシート名（`シート1`）をダブルクリックし、**`triage`** に変更します
3. 1行目に次の見出しを入力します

| A | B | C | D | E | F | G | H |
|---|---|---|---|---|---|---|---|
| 処理日時 | 受信日時 | メッセージID | 差出人 | 件名 | 分類 | 確信度 | 要約 |

4. **3-2A（サービスアカウント）の場合のみ**、右上の「共有」を押し、3-2A(1)のJSONファイルに書かれている `client_email` の値（`〜@〜.iam.gserviceaccount.com` という形式のアドレス）を **編集者**として追加します
   （3-2B（OAuth）の場合は自分のアカウントで書き込むため、共有の設定は要りません）
5. ブラウザのアドレスバーのURLから、**スプレッドシートID**を控えます

```
https://docs.google.com/spreadsheets/d/【ここがスプレッドシートID】/edit
```

### 3-3. Slack の通知先を用意する

1. https://api.slack.com/apps を開き、「Create New App」→「From scratch」を選びます
2. アプリ名に `メール振り分け通知` と入力し、対象のワークスペースを選びます
3. 左メニュー「Incoming Webhooks」を開き、スイッチを **On** にします
4. 「Add New Webhook to Workspace」を押し、通知先のチャンネルを選んで許可します
5. 表示された `https://hooks.slack.com/services/...` というURLをコピーします

> このURLを知っている人は誰でもそのチャンネルに投稿できます。**外部に共有しないでください。**

---

### 3-4. GitHub に設定を登録する

ここまでで集めた情報を GitHub に登録します。

対象のリポジトリの画面で「Settings」タブ → 左メニュー「Secrets and variables」→「Actions」を開きます。

#### Secrets（秘密の情報）

「New repository secret」を押して登録します。**一度登録すると中身は二度と表示されません**（上書きはできます）。

共通のもの。

| 名前 | 入れる値 |
|---|---|
| `ANTHROPIC_API_KEY` | 手順3-1で取得した `sk-ant-` で始まる文字列 |
| `SLACK_WEBHOOK_URL` | 手順3-3でコピーした `https://hooks.slack.com/services/...` |

**3-2A（Google Workspace / サービスアカウント）を選んだ場合**は、これも登録します。

| 名前 | 入れる値 |
|---|---|
| `GOOGLE_SERVICE_ACCOUNT_JSON` | 手順3-2A(1)でダウンロードしたJSONファイルの中身を**すべてコピーして貼り付け** |

> JSONファイルをメモ帳などで開いて、`{` から `}` まで全部をそのまま貼り付けてください。改行が入っていても構いません。

**3-2B（個人のGmail / OAuth）を選んだ場合**は、これらを登録します。

| 名前 | 入れる値 |
|---|---|
| `GOOGLE_OAUTH_CLIENT_ID` | 手順3-2B(3)のクライアントID |
| `GOOGLE_OAUTH_CLIENT_SECRET` | 手順3-2B(3)のクライアントシークレット |
| `GOOGLE_OAUTH_REFRESH_TOKEN` | 手順3-2B(4)で取得した `1//` で始まる文字列 |

#### Variables（秘密でない設定）

「Variables」タブに切り替え、「New repository variable」から次を登録します。

| 名前 | 入れる値 | 例 |
|---|---|---|
| `GMAIL_USER` | 対象のメールアドレス（**3-2A のみ必要**。3-2B では不要） | `info@example.co.jp` |
| `GMAIL_QUERY` | 取得するメールの条件 | `is:unread -category:promotions` |
| `SHEETS_SPREADSHEET_ID` | 手順3-2(3)で控えたID | `1AbC...XyZ` |
| `SHEETS_RANGE` | 記録先の範囲 | `triage!A:H` |
| `TRIAGE_MAX_MESSAGES` | 1回に処理する上限件数 | `20` |
| `TRIAGE_CONFIDENCE_THRESHOLD` | 保留にする基準 | `0.6` |

設定は以上です。

> **`TRIAGE_ENABLED` はまだ登録しないでください。**
> これは自動実行の入り切りスイッチです。次の「4. 動作確認」がすべて終わってから登録します。
> 登録するまで、定期実行は動きません（手動実行だけができる状態です）。

## 4. 動作確認

**いきなり本番を動かさないでください。** 次の順番で確認します。

### 手順1: サンプルデータで動かす（外部に一切影響しません）

GitHubの「Actions」タブを開き、左メニューから **CI** を選んで「Run workflow」を押します。

緑のチェックが付けば、プログラム自体は正しく動いています。ここではメールもスプレッドシートも一切触っていません。

### 手順2: 本物のメールで、書き込みなしで動かす（ドライラン）

「Actions」タブ →「メール振り分け」→「Run workflow」を押し、**「書き込みを行わず分類結果だけ確認する」にチェックを入れて**実行します。

実行が終わったら、実行結果をクリックして「実行」のログを開きます。最後に次のような表が出ています。

```
  実行結果 (本番 / ドライラン)
  取得        : 12 件
  処理        : 12 件
  保留        : 2 件 (うち確信度 0.6 未満による差し戻し 1 件)
  ...
  分類の内訳:
    新規問い合わせ　　　 3 件
    見積依頼　　　　　　 1 件
    ...
```

**ここで確認すること:**

- 取得件数が想定と合っているか（0件なら `GMAIL_QUERY` の条件を見直す）
- 分類が実際のメールと合っているか（ログを上にたどると1通ずつの分類結果が出ています）
- 保留が多すぎないか（全体の2割を超えるようなら担当エンジニアに相談してください）

この時点でも、スプレッドシートにもSlackにもGmailにも**一切書き込まれていません**。何度でもやり直せます。

### 手順3: 本番で1回だけ動かす

「Run workflow」を、今度は**チェックを入れずに**実行します。

実行後、次の3点を確認してください。

- [ ] スプレッドシートに行が追加されている
- [ ] Slackに通知が届いている（要対応のものだけ）
- [ ] Gmailの「下書き」フォルダに下書きができている

### 手順4: もう一度、同じ設定で動かす

続けてもう一度「Run workflow」を実行します。

- [ ] スプレッドシートの行が**増えていない**
- [ ] Slackに**同じ通知が再度来ていない**

同じメールを二度処理しない仕組みが効いていることの確認です。ここで行が増えるようなら、担当エンジニアに連絡してください。

## 5. 本番稼働の開始

手順4まで確認できたら、自動実行を有効にします。

「Settings」→「Secrets and variables」→「Actions」→「Variables」タブで、次を登録してください。

| 名前 | 値 |
|---|---|
| `TRIAGE_ENABLED` | `true` |

これで平日の 9時・13時・17時 に自動で動きます。**止めたくなったら、この値を `false` に変えるだけです**（削除でも構いません）。

ただし、**いきなり従来の目視確認をやめないでください。** 次の順で移行することを推奨します。

| 期間 | やること |
|---|---|
| 1〜2週目 | 自動実行と並行して、従来通り目視でも全件確認する。分類のズレを記録する |
| 3〜4週目 | Slack通知を主にして対応する。目視確認は1日1回に減らす |
| 5週目〜 | 目視での全件確認をやめる。保留の通知だけ必ず見る |

1〜2週目で分類のズレが目立つ場合は、担当エンジニアに具体例（どんなメールが、何に分類されるべきで、実際は何になったか）を伝えてください。基準の調整ができます。

## 6. 日々の運用

### 毎日やること

**Slackの通知を見て対応する。それだけです。**

通知はこの形式で届きます。

```
:mailbox_with_mail: 【見積依頼】要対応のメールが届いています
差出人: suzuki@example.co.jp
件名: 【見積依頼】システム開発費用について
要約: 在庫管理システムの見積依頼。想定30名、納期2027年3月末。
確信度: 0.90
判断根拠: 見積という語と具体的な要件が含まれるため
```

保留の場合はこうなります。

```
:warning: 【保留】確信度不足のため人の確認が必要です（元判定: inquiry）
```

**この通知が来たら、必ずGmailで実物を確認してください。** AIが判断できなかったものです。

返信する場合は、Gmailの「下書き」に用意されている文面を確認・修正して送信します。下書きは**そのまま送らず、必ず内容を確認してください**。

### 週に1回やること

スプレッドシートを開き、次を確認します。

- [ ] 保留の件数が急に増えていないか（増えていれば、いつもと違う種類のメールが届き始めた可能性）
- [ ] 明らかに分類がおかしい行がないか（あればメモしておき、月次でまとめて相談する）

### 月に1回やること

- [ ] Anthropic の利用料を確認する（https://console.anthropic.com/ の「Usage」）
- [ ] 分類のズレをまとめて担当エンジニアに共有する

## 7. 困ったときは

### Slackに通知が来ない

| 確認すること | 対応 |
|---|---|
| そもそも実行されているか | GitHubの「Actions」タブで実行履歴を確認する |
| 実行が失敗（赤い×）していないか | 下の「実行が失敗している」を参照 |
| 対象のメールが届いているか | 要対応の区分のメールが0件なら通知は来ない（正常） |
| Webhook URLが正しいか | 手順3-3をやり直し、Secretを登録し直す |

### 実行が失敗している（赤い×が付く）

「Actions」タブで失敗した実行をクリックし、赤い×が付いたステップを開くと、末尾にエラーが出ています。

| エラーの表示 | 原因 | 対応 |
|---|---|---|
| `設定エラー: ANTHROPIC_API_KEY が設定されていません` | Secretの登録漏れ | 手順3-4を確認する |
| `設定エラー: Google連携の設定が不足しています` | Variablesの登録漏れ | 手順3-4のVariablesをすべて登録する |
| `401` / `invalid x-api-key` | APIキーが誤っている、または失効 | APIキーを作り直してSecretを更新する |
| `403` / `insufficient permission` | Googleの権限設定 | 手順3-2(2)のスコープ設定をやり直す |
| `Slack通知に失敗しました (HTTP 404)` | Webhook URLが無効 | 手順3-3をやり直す |
| `429` / `rate limit` | APIの利用制限 | 自動で3回まで再試行される。それでも失敗する場合は `TRIAGE_MAX_MESSAGES` を減らす |
| `invalid_grant` / `Token has been expired or revoked` | **OAuthのリフレッシュトークンが失効した** | 下の「1週間ほど動いていたのに、急に毎回失敗するようになった」を参照 |

### 1週間ほど動いていたのに、急に毎回失敗するようになった（OAuthの場合）

**OAuth同意画面が「テスト」状態のまま取得したリフレッシュトークンは7日で失効します。** 症状がこの形（設定を何も変えていないのに、ある日から全部失敗する）なら、まずこれを疑ってください。

1. https://console.cloud.google.com/ →「APIとサービス」→「OAuth同意画面」を開く
2. 公開ステータスが「テスト」なら「アプリを公開」で**本番環境に切り替える**
3. `npm run auth:google` を実行し直し、新しい `GOOGLE_OAUTH_REFRESH_TOKEN` をSecretに登録し直す

**失敗した実行で処理できなかったメールは、次回の実行で自動的に処理されます。** 慌てて手動で実行し直す必要はありません。

### 同じメールが二重に処理された

処理済みの記録が失われた可能性があります（GitHub Actions に保存している記録は90日で消えます）。担当エンジニアに連絡してください。スプレッドシートの重複行は手で削除して構いません。

### 分類がおかしい

まず「どんなメールが」「何に分類されるべきで」「実際は何になったか」を記録してください。数件たまったら担当エンジニアに渡します。

**急ぎで安全側に倒したい場合**は、`TRIAGE_CONFIDENCE_THRESHOLD` を `0.6` から `0.8` に上げてください。AIが少しでも迷ったメールが保留になり、人の確認に回ります。**確認する手間は増えますが、見落としは減ります。**

### 利用料が想定より高い

`TRIAGE_MAX_MESSAGES` を下げてください（例: `20` → `10`）。1回の実行で処理する上限件数です。

### いったん止めたい

「Settings」→「Secrets and variables」→「Actions」→「Variables」で `TRIAGE_ENABLED` を `false` に変更してください。次回以降の自動実行が止まります。再開は `true` に戻すだけです。

## 8. 設定値の一覧

| 名前 | 種別 | 必須 | 既定値 | 説明 |
|---|---|:---:|---|---|
| `ANTHROPIC_API_KEY` | Secret | ○ | – | Claude API のキー |
| `GOOGLE_SERVICE_ACCOUNT_JSON` | Secret | 3-2Aなら○ | – | サービスアカウントのJSONキー |
| `GOOGLE_OAUTH_CLIENT_ID` | Secret | 3-2Bなら○ | – | OAuthクライアントID |
| `GOOGLE_OAUTH_CLIENT_SECRET` | Secret | 3-2Bなら○ | – | OAuthクライアントシークレット |
| `GOOGLE_OAUTH_REFRESH_TOKEN` | Secret | 3-2Bなら○ | – | `npm run auth:google` で取得。**「テスト」状態で取ると7日で失効する** |
| `GOOGLE_AUTH_MODE` | Variable | – | 自動判定 | `service_account` / `oauth`。両方の設定がある場合のみ必要 |
| `SLACK_WEBHOOK_URL` | Secret | – | – | 未設定ならログ出力のみ |
| `GMAIL_USER` | Variable | 3-2Aなら○ | – | 委任先のメールアドレス。3-2B では不要 |
| `GMAIL_QUERY` | Variable | – | `is:unread -category:promotions` | 取得条件。Gmailの検索窓と同じ書き方 |
| `SHEETS_SPREADSHEET_ID` | Variable | ○ | – | 記録先スプレッドシートのID |
| `SHEETS_RANGE` | Variable | – | `triage!A:H` | 記録先のシート名と範囲 |
| `TRIAGE_MODEL` | Variable | – | `claude-opus-5` | 分類に使うモデル |
| `TRIAGE_MAX_MESSAGES` | Variable | – | `20` | 1回の処理上限件数 |
| `TRIAGE_CONFIDENCE_THRESHOLD` | Variable | – | `0.6` | この値未満の確信度は保留に倒す（0.0〜1.0） |
| `TRIAGE_ENABLED` | Variable | – | 未設定 | `true` のときだけ定期実行が動く。稼働の入り切りスイッチ |

### 確信度の閾値について

| 設定値 | 挙動 | 向いている状況 |
|---|---|---|
| `0.4` | ほとんど保留にならない | 分類のズレより手間の削減を優先したい |
| `0.6`（既定） | 迷いのあるものが保留になる | 通常の運用 |
| `0.8` | 少しでも迷えば保留になる | 見落としを絶対に避けたい導入初期 |

**迷ったら高めにしてください。** 保留が増えて確認の手間は増えますが、見落としは減ります。慣れてきたら下げていく方が安全です。

## 付録: ローカルPCで動かす場合

担当エンジニア向けの補足です。

```bash
# 1. 依存関係をインストール
npm install

# 2. サンプルデータで動作確認（APIキー不要）
npm run demo

# 3. 本番設定で動かす場合
cp .env.example .env   # エディタで値を埋める
npm run dry-run        # 書き込みなしで確認
npm start              # 本番実行
```

実行ログは1行1JSONで標準出力に出ます。絞り込みには `jq` が使えます。

```bash
node dist/index.js | jq 'select(.event == "message.classified")'
```

```bash
node dist/index.js | jq 'select(.level == "error")'
```
